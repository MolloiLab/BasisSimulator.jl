## 3. Programming model

- `@compile f(args...)` returns a Thunk; `@jit` compiles and runs; `Reactant.to_rarray` converts arrays (and structs recursively) to `ConcreteRArray` (an alias for `ConcretePJRTArray` or `ConcreteIFRTArray` depending on the `xla_runtime` preference; PJRT is default, IFRT is needed for sharding). Plain numbers are frozen as constants unless `track_numbers=true` (`docs/src/introduction/FAQs.md`, `tutorials/partial-evaluation.md`).
- Tracing semantics (`tutorials/control-flow.md`): Julia `if`/`for` on non-traced values is specialized/unrolled at trace time. Data-dependent control flow needs `@trace`: `if`/`elseif`, `for` over integer ranges (static or traced bounds), `while`; not allowed: mutation inside a `while` condition, arbitrary iterables, type-unstable branches; `&&`/`||` become `&`/`|` (ReactantCore docstring). Unwrapped loops explode codegen: a Lux model took 2 to 3 min and 7 to 10 GB to compile until the time loop got `@trace` (discourse 132655).
- Static shapes only: "Reactant arrays do not yet support dynamic dimensions" (mofeing, issue #2809, 2026-04-11). A thunk is valid only for the same types and sizes (README).
- Mutation: `setindex!`/`.=` on traced arrays lowers to `dynamic_update_slice`/scatter and the updated value is returned and written back to the caller's `ConcreteRArray` (FOSDEM'26 slides 18 to 19; README). `donated_args=:auto` donates buffers not preserved by the function; `assert_nonallocating=true` enforces zero new output buffers (`src/CompileOptions.jl`).
- Available ops (`src/Ops.jl` inventory, clone): gather, scatter, dynamic_slice, dynamic_update_slice, reduce, reduce_window, convolution, fft, sort, top_k, approx_top_k, argmax, findfirst, while_loop, if_condition, case, rng_bit_generator, randn, randexp, cholesky, lu, svd, batch, hlo_call, julia_callback, ignore_derivatives. Base overloads: `sort/sort!/sortperm/partialsort` (`src/TracedRArray.jl:634-767`), `findfirst` (:848), `findmax`, `accumulate/cumsum` (:972), `mapreducedim!` (sum over dims), linear algebra via `src/stdlibs/LinearAlgebra.jl` (gaps: `eigvals!` #2127, matrix `exp` #1565).
- Indexing: `getindex` with traced integer indices lowers to `dynamic_slice` (`src/Indexing.jl:29`); `setindex!` with traced indices to scatter (:370-379); `Reactant.@allowscalar` is re-exported from GPUArraysCore. Scalar loops written under `@trace for` are "raised" to tensor IR by default (`disable_loop_raising_passes=false`; `tutorials/raising.md` N-body example).
- FFT: AbstractFFTs ext gives `fft, ifft, rfft, irfft`, in-place variants and plans (FFTW plans are converted); StableHLO wants the transformed dims to be the trailing dims, otherwise the ext inserts `permutedims` (`ext/ReactantAbstractFFTsExt.jl`). Complex arrays are traced natively.
- Sharding: `Sharding.NamedSharding(Sharding.Mesh(devices, (:x,:y)), (:x, nothing))` at allocation, IFRT preference required; irrelevant on one Mac, useful on a multi-GPU node.
- Caching: there is no automatic type/shape-keyed cache. Hold the Thunk (`@jit` docstring: "Most users should use `@compile` instead to cache the compiled function"; wsmoses, discourse 137429, 2026-06-03). A persistent XLA autotune cache is on by default; the kernel/compile cache is off (`tutorials/persistent_compile_cache.md`).
- Fusion: Enzyme-JAX MLIR passes (`optimization_passes=:all`) plus XLA fusion; `sync=false` is the default (async dispatch), use `sync=true` or `Reactant.synchronize` for timing.

## 4. Enzyme inside Reactant

- Inside a traced function, `Enzyme.autodiff` / `Enzyme.gradient` with `Forward`, `Reverse`, `ReverseWithPrimal`, `Duplicated`, `Const`, `Active`, `BatchDuplicated` are intercepted (`overload_autodiff`, `src/Enzyme.jl:313`) and emitted as `enzyme.autodiff` / `enzyme.fwddiff` MLIR ops (`src/Enzyme.jl:473`). EnzymeMLIR differentiates the StableHLO, not Julia LLVM, so Enzyme.jl's LLVM-level limitations (activity errors, GC, type instability) do not apply to traced code. Nested AD, strong-zero mode and `ignore_derivatives` work (`tutorials/automatic-differentiation.md`).
- Custom rules: Julia `EnzymeRules.forward/augmented_primal/reverse` are NOT honored for traced code (the primal is traced to MLIR first). Issue #487 "Register custom adjoints" is open since 2025-01-06 (wsmoses: needs EnzymeMLIR support for a call op with a registered derivative). `@reactant_overlay` (`src/Interpreter.jl:21`) can substitute a different implementation during tracing but is not a derivative rule. `Ops.julia_callback` has no reverse adjoint (#3040). Enzyme.jl also cannot differentiate a compiled Thunk from outside (#2552, open).
- Loops and memory: `@trace checkpointing=true` (isqrt(N) checkpoints for static-bound `for`), `checkpointing=Periodic(n)` (mandatory for `while` or traced bounds), `mincut=true` to recompute instead of store (ReactantCore `@trace` docstring; AD tutorial). Known bugs: forward-mode AD through a `@trace` loop fails with a `stablehlo.while` shape mismatch (#2361, open 2026-02-05); repeated loop inputs create invalid IR (#570); NaN gradients in reduce-slice fusion (#3191, 2026-08-15); nested AD through `NNlib.conv` silently wrong (#3064).
- Kernels: Enzyme within Reactant can only differentiate raised kernels; compile with `raise=true raise_first=true` (`tutorials/kernels.md`).

## 5. Random numbers

- `ReactantRNG(seed::Vector{UInt64} (length 2), algorithm)` with algorithm "DEFAULT", "PHILOX" or "THREE_FRY" (`src/Types.jl:648`, `Ops.rng_bit_generator` docstring). `rand/randn/randexp` and in-place forms are traced (`src/stdlibs/Random.jl`); `Random.default_rng()` inside a trace yields a fresh ReactantRNG; any other RNG is converted with a warning about "different seed and distribution characteristics"; `Random.seed!` takes a number or a `TracedRArray` seed (a `TracedRNumber` seed errors). The seed state is threaded through the graph, so runs are reproducible per seed and algorithm; PHILOX/THREE_FRY are deterministic across backends, "DEFAULT" is backend-specific.
- No Poisson sampler: no "poisson" anywhere in `src/` or `ext/`, no Distributions extension in 0.2.285.

## 6. KernelAbstractions / CUDA.jl kernels

- `ReactantKernelAbstractionsExt` defines `ReactantBackend <: KA.GPU`; a kernel launch on traced arrays is intercepted with `@reactant_overlay` and routed to `ka_with_reactant`. Compilation of the kernel body happens in `ReactantCUDAExt` (CUDA + Enzyme + GPUCompiler + KA + LLVM), so CUDA.jl must be loaded "even on non-NVIDIA hardware" (`tutorials/kernels.md`). The kernel is compiled to LLVM, then either launched as a real CUDA kernel (CUDA backend) or "raised" to StableHLO (`raise=true`; automatic for TPU and sharded inputs). This is the Polygeist-style path shown in the FOSDEM'26 slides (Giordano & Merckx, 2026-02-01, slide 15: compile to LLVM, raise structure in MLIR, multi-dimensionalize into tensor ops, optimize).
- On CPU/macOS the only path is raising. `test/integration/kernelabstractions.jl` starts with `using CUDA` and runs in the `integration` group on `macOS-latest` CI (no `Sys.isapple` gate), so KA kernels do compile on Macs via raising.
- Limits: "Not all classes of kernels are currently raisable" (`tutorials/raising.md`). Open: `@localmem` kernels fail to raise with `!llvm.ptr<3>` (#3019), Real<->Complex inside raised kernels (#2406), `llvm.mlir.addressof` of Julia scalar globals (#3043), vectorization of polybench kernels (#2249), TPU clamp (#3117). Kernels with atomics, shared memory, data-dependent early exits or per-thread while loops are the risky class.
- AcceleratedKernels.jl: no extension; issue #1625 (open, 2025-09-03) says AK's `mapreduce` etc. must be overlaid to Base ops; AK's KA kernels use `@localmem` and atomics, so treat AK as incompatible today.

## 7. Performance notes

- XLA CPU client: `GetPjRtCpuClient(CpuClientOptions{asynchronous=true})` (`deps/ReactantExtra/API.cpp:515`); Eigen thread pool sized from core count; no Julia-level knob. Issue #3019 (2026-06-30, batched ComplexF64 inner product) reports on a 10-core Mac: 11.00 ms single-thread vs 11.15 ms 10-thread for `dot_general` (multithreading gave nothing) and a 2.5x win on an M4 Pro just by making the contraction dim contiguous; the maintainer's analysis suggests `TF_NUM_INTRAOP_THREADS` to cap threads (not verified in Reactant source). Discourse 135559 (Feb 2026): the "200x" CPU speedup was constant folding; corrected numbers were of the same order as native Julia, so on CPU expect fusion wins on elementwise/reduction chains, not miracles on memory-bound gathers.
- Compile time and memory: minutes and several GB for medium graphs (discourse 132655; avik-pal: 2-minute first compile "not unexpected"); precompiling Reactant itself can exhaust RAM (#3051, open 2026-07-10; #2889 precompile regression in 0.2.260). On a 16 GB M4 this is the primary risk: compile stages as separate thunks and keep graphs small with `@trace` loops.
- Memory: device buffers are freed by Julia finalizers; call `GC.gc()` between large calls (FAQ); GPU-only knobs `XLA_REACTANT_GPU_MEM_FRACTION` (0.75) and `XLA_REACTANT_GPU_PREALLOCATE`. `donated_args=:auto` enables in-place updates.
- Precision: no Float64 demotion; f64 is traced as `tensor<...xf64>` and runs on CPU and CUDA (TPU lacks it; the Metal PR downcasts). Opt-in `MultiFloatOptions` converts f64 to double-f32. `Reactant.with_config(dot_general_precision=PrecisionConfig.HIGH)` fixes CUDA TF32 mismatches.
- `@compile sync=true` blocks until the computation completes; the default returns immediately after scheduling (FAQ, `SYNC_DOCS`). Use `Reactant.@time/@timed/@profile`.

- Lux: `reactant_device()`, `Training.TrainState` with `AutoReactant()`/`AutoEnzyme()`, Optimisers `Adam` documented (Lux "compiling_lux_models"); `test/integration/optimisers.jl` exists.
- NNlib ext: `conv` (`Ops.convolution`), `gather!`, `scatter!`, `batched_mul`, `pad_constant`, pooling via `reduce_window`, `upsample_linear`, `unfold/fold`, softmax.
- Host callback exists: `Ops.julia_callback(f, result_specs, args...; has_side_effect)` (PR #2580, 2026-03-01), CPU and CUDA only, single device, no reverse adjoint. `Ops.hlo_call` embeds StableHLO text. PythonCall ext for JAX interop. Zygote is overlaid to Enzyme but unsupported on 1.12.

## 9. 2026 pain points (issues cited above plus)

Compile-time blowups and memory (132655, #3051), no dynamic shapes (#2809, #2721), Metal absent, LinearAlgebra gaps (#2127, #1565), `@trace` scope bug inside `@testset` (#2582), NaN gradients (#3191, #2973), `:all` pass pipeline non-termination on bf16 graphs (#3225), aarch64 Linux + new NVIDIA drivers (#3112), 1.12-only kernel bug (#2926), 1.13 not yet green (#2817). `sort`, `findfirst`, `partialsort` and complex FFT on CPU/GPU all exist now (the 2025 gather/scatter discourse complaint is resolved by `Ops.gather/scatter` and the NNlib ext).

## Implications for the CT pipeline

Global rules: fix `(n_col, n_row, n_view, n_E, nx, ny, nz)` at compile time; pass every runtime scalar (mA, kVp scale, strength) through `to_rarray(...; track_numbers=true)`; use Float32; compile the forward model and the recon as separate thunks and hold them; wrap every view/iteration loop in `@trace for` so the graph stays small; run with `sync=true` when timing; on the Mac everything is XLA-CPU, on Linux the same thunks run on CUDA.

| Stage | Mapping | Notes |
|---|---|---|
| 3D cone-beam distance-driven forward projection | Reformulate as a tensor program; do not port the KA `dd_fast` kernels | Per view: precompute boundary-projection index tensors and weights on the host or in-graph, express the DD overlap integral as `cumsum` along the detector axes (integral image) plus `Ops.gather`/indexing with integer index tensors, then per-material path-length sums via broadcasting. `@trace for` over views (or z-slabs) with `dynamic_update_slice` accumulation. Raising the existing KA kernels is possible in principle (needs `using CUDA` even on the Mac) but branchy overlap logic and any `@localmem`/atomics are the known raising failure class (#3019, #3043). Gather has a scatter adjoint in EnzymeMLIR, so reverse AD is free. |
| Polychromatic spectrum integration | Straightforward array program | Broadcast `exp.(-Σ_m μ_m(E)·L_m)` over a static energy axis and `sum(dims=E)`; if `n_E × sinogram` exceeds memory, `@trace for` over energy bins with an accumulator. |
| Detector response (DRM/UFC LUT) | Straightforward | Energy-response matrix multiply or `NNlib.conv` along E; LUTs become gather with static index tensors. |
| Poisson noise | Reformulate as an input tensor | No Poisson sampler; generate counts (or a unit-normal ε) on the host and pass them in, or use a Gaussian surrogate `λ + sqrt(λ)·ε` with `ε` from `randn(ReactantRNG)` inside the graph; wrap sampling in `ignore_derivatives`/`Const`. |
| FDK/FBP ramp filter + backprojection | Straightforward plus `@trace` loop | `rfft/irfft` along the column axis (make it the trailing dim, or accept the inserted permutedims); cosine/Parker weights as broadcasts; backprojection as trilinear/bilinear interpolation with precomputed integer index tensors + weights via `Ops.gather`, accumulated over views in `@trace for`. Linear, so AD is exact. |
| Iterative PWLS recon | `@trace for` (fixed iterations) or `@trace while` (tolerance) | Forward/back projectors as plain functions inside the loop; reverse AD needs `checkpointing=Periodic(n)` (or `mincut=true`) or memory scales with iterations; no custom rule for implicit differentiation, so either unroll-and-checkpoint or write the implicit-function derivative explicitly as a forward computation. Forward-mode through `@trace` loops is currently broken (#2361). |
| Sinogram-domain material decomposition with root-finding | Reformulate to branchless vectorized Newton | Per-ray 2×2 Newton with a fixed iteration count under `@trace for`, all per-element branching as `ifelse`/`clamp`; Brent-style bracketing with per-element early exit does not trace. For gradients, either unroll the iterations or compute dp/dy = -J⁻¹ ∂F/∂y explicitly (manual derivative, since custom rules are unavailable). |
| Bilateral / SVD denoising | Straightforward | Per-row SVD via batched `svd` (`Ops.svd`, `Ops.batch`); bilateral filter as fixed-window shifted-slice or `reduce_window` sums with `exp` range weights; fully broadcastable and differentiable. Edge-aware joint bilateral is the same pattern. |

What stays outside the graph: reading spectra/phantoms, Poisson sampling, plotting, and any code path needing dynamic shapes (variable number of views or variable-size ROI).

Open questions the lead may want to decide: whether to invest in the raising path for the existing KA projector (fast to try: `using CUDA; @code_hlo raise=true dd_forward(...)` on the Mac) versus a clean gather/cumsum DD formulation (recommended), and whether the 16 GB M4 is viable for compiling a full-volume 3D graph at all before an NVIDIA box is available.
